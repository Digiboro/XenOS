# Правила работы с lint-ами и диагностиками

## expect vs allow

Предпочитайте `#[expect(...)]` вместо `#[allow(...)]` где это возможно.

### Почему expect лучше

`#[expect]` предупредит если lint больше не срабатывает, что помогает:

- Не забыть удалить временные подавления
- Заметить когда код изменился и подавление больше не нужно
- Отслеживать улучшения в компиляторе/Clippy

```rust
// Хорошо: expect предупредит когда f() начнёт использоваться
#[expect(dead_code)]
fn f() {}

// Плохо: allow останется навечно даже когда станет не нужен
#[allow(dead_code)]
fn f() {}
```

### Когда использовать allow

Используйте `#[allow]` вместо `#[expect]` когда:

1. **Условная компиляция** — lint срабатывает только при определённых feature/cfg:

   ```rust
   #[allow(dead_code)] // Используется только с feature = "test-kernel"
   fn test_helper() {}
   ```

2. **Макросы** — разные вызовы макроса создают разное поведение

3. **Архитектурные различия** — код ведёт себя по-разному на разных платформах:
   ```rust
   #[allow(clippy::unnecessary_cast)] // Нужен на некоторых архитектурах
   let size = len as usize;
   ```

## Условный expect

Если lint срабатывает только в определённой конфигурации, можно использовать условный expect:

```rust
#[cfg_attr(not(feature = "test-kernel"), expect(dead_code))]
fn test_only_function() {}
```

Используйте это только если конфигураций мало (1-2), иначе проще использовать `#[allow]`.

## Стандартные подавления в проекте

Для no_std ядра типичны следующие подавления на уровне crate:

```rust
#![allow(internal_features)]      // Использование internal features
#![allow(incomplete_features)]    // Нестабильные features
```

## Документирование подавлений

При подавлении lint-а добавляйте комментарий с причиной:

```rust
#[expect(clippy::too_many_arguments)] // NT API требует эти параметры
pub fn NtCreateFile(...) {}
```
